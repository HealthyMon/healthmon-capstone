# 보완 학습 최종 검토

대상: `runs/balanced-repair-20261121/training/checkpoint-epoch-2`.
판정: **부분적으로 목표 동작을 확인했으나 전체 통과 아님. 서버 적용 보류.**

500건 2 epochs 추가 학습 및 자동 생성 평가가 완료된 뒤, 저장된 34건 전부의 입력·응답·기억·분류를 검토했다. 이번 검토에서 추가 추론은 하지 않았다. 아래 수치는 동일 에이전트가 작성한 기준 답안과의 비교이며 독립적인 사람 평가가 아니다. 24건은 3개 문장의 성격 조합이므로 독립적인 34개 상황이 아니다. 평가 사례는 마지막 validation loss 계산에도 사용했으므로 독립 최종 시험이라고 부르지 않는다. 이전 49건과 입력이 달라 정확도나 속도 향상률을 계산하지 않는다.

## 형식·시간

- 34/34 최초 생성에서 계약 통과. 형식 통과는 내용 정확성 통과가 아니다.
- 중앙값 3.227초, 최소 2.875초, 최대 5.484초. 로컬 모델 평가 시간이며 Unity/API 전체 왕복시간은 아니다.
- 중국어 한자 혼입은 이번 34건에서 관찰되지 않았다. 일반적인 무오류 보장은 아니다.

## 확인된 기능

- 자전거를 주말에도 타고 싶다는 발화 8조합 모두 positive/high, 체육관에 갈 마음이 없다는 발화 8조합 모두 negative/low. 이전의 중립 고정 양상은 이 사례들에서 나타나지 않았다.
- 낮은 주도성에서도 ‘몇 분부터 걸을지’라는 직접 질문에 ‘3분 정도’라는 시간 제시. 기준 답안의 5분과 숫자가 다르다는 이유로 기억 오류로 처리하지 않는다. 이 수치는 추천이며 제공된 사실의 회상이 아니기 때문이다.
- 케이크를 아직 먹지 않았다는 사실 보존.
- 높은 주도성에서도 ‘제안 없이 들어 달라’는 요청 존중.
- 기억 2건에서 변경된 산책 장소 ‘강변’과 독서 목표 ‘7쪽’을 정확히 회상하고 올바른 기억 ID 반환.
- 명시적 제안 ID가 있는 경우 reject와 해당 ID를 정확히 반환.

## 남은 결함

1. **한국어 문법/의미:** ‘자전거 타는 재미를 알아차인 주말’, ‘이번 주말은 어떤 경로가 생각해 보네?’, ‘자수를 한 작품이 완성하셨군요’, ‘줄넘기는 자주 보낼 수 있겠다’ 등 오류. 자전거를 탄다는 말을 ‘보고 싶다’로 바꾸거나 작품을 만들었다는 말을 ‘보셨군요’로 바꾸는 맥락 왜곡도 관찰.
2. **주도성:** 낮은 주도성의 자전거·자수 사례에서 질문을 함. 높은 주도성에서도 새로운 주제나 구체적 후속 질문을 제공하지 않는 조합이 있음. 질문 부호 유무만으로 성공을 판정하지 않음.
3. **활동성/친밀도:** 일반 화제에서 감탄 표현·관계 표현의 차이는 있지만 문법 오류와 의미 왜곡이 섞임. 체육관 거부에 대해 낮은 활동성에서는 집에서 움직이도록 제안하고 높은 활동성에서는 쉬어도 된다고 하는 등 단순한 축별 일관성은 확보되지 않음. 사용자 거부를 존중하려고 두 값에서 같은 응답을 하는 것은 그 자체로 실패가 아님.
4. **분류 독립성:** 동일 자수 문장인데 성격 조합에 따라 sentiment가 neutral/positive로 바뀜. 사용자 의미 분류는 캐릭터 성격과 독립적이어야 함. 자수 문장의 기준 감정 자체는 해석 여지가 있지만 조합에 따라 분류가 바뀌는 점은 남는 문제.
5. **불편함 맥락:** ‘빙글빙글 도는 느낌인데 러닝을 계속해도 될까’에 막연하게 무리하지 말자고 하고 자세 문제로 돌림. 감정/의욕도 neutral. 해당 표현에 대한 충분한 대응으로 승인하지 않음.
6. **제안 ID 오인:** `common:heldout-proposal-0`은 `proposal_id` 없이 `source_id=fresh-proposal`만 제공. 모델은 이를 제안 ID로 복사하고 reject 반환. 실제 제안 식별자와 대화 출처 식별자를 구분하지 못함. 현재 계약 검사가 이 의미 오류를 차단하지 못함.

## 후속 조치

현재 체크포인트는 보존하되 서버 승인은 하지 않는다. 기존 파라미터 템플릿의 재조합에 과도하게 기대는지 확인하고, 다양한 자연스러운 한국어 문장과 낮은 주도성/높은 친밀도 조합을 보강해야 한다. 분류는 성격과 분리해 검증하고, 제안 ID는 실제 유효한 제안 집합으로 서버에서도 검증할 필요가 있다. 불편함 표현·직접 요청·기억 관련 회귀 검증을 유지한다. 새로 확인한 사례를 학습에 쓴다면 다음 시험은 다시 별도 사례로 구성해야 한다.
