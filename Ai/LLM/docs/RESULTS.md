# 실행 결과

기준: 2026-09-29, Windows 11 / RTX 3090 24GB / 프로젝트 전용 Python 환경.

완료: 공식 Qwen3.5-9B 원본 19,306,310,880바이트·775개 인덱스 텐서 점검, BF16 추론, BGE-M3 CPU 임베딩, PostgreSQL 17.11 + pgvector 0.8.2, API 구현, 실제 BF16 LoRA 학습/저장/재로딩. DB 재시작 전후 펫·기억 벡터·보상 원장 동일성을 확인했다.

파일럿 학습: 학습 34건, 검증 8건, 3 epochs(102 sample visits), optimizer 15회. 텍스트 LoRA trainable 21,639,168개. 약 259.9초. validation loss 0.741445 → 0.647154 → 0.592772. 3회차 어댑터를 개발 후보로 선택했고 재로딩 loss도 동일했다. 마지막 파일이라는 이유로 선택하지 않았다.

메모리: 첫 smoke allocated 19.9166GiB / reserved 25.5313GiB로 Windows WDDM에서 느려짐을 관측. 캐시 반환 조정 후 파일럿 allocated 최대 20.1762GiB / reserved 20.4473GiB. 각 학습 backward 직후 nvidia-smi 표본 최대 22,501MiB(장치 전체, 데스크톱 사용 포함). 이 마지막 값은 연속 계측 최대값이 아니라 표본 최대다.

초기 동일 검증셋 8건 비교: JSON 문법은 기본/LoRA 모두 8/8. 당시 응답 계약과 ID 검사는 기본 7/8, LoRA 8/8. 평균 생성 시간 6.22초 → 4.89초. 자연어 의미 정확도나 최종 test 성능이 아니다. 초기 난수 시드는 모델 로딩 전에 설정되어 어댑터 초기화가 RNG 소비에 영향을 줄 수 있었으므로, 마지막 비교는 각 예제 생성 직전에 난수를 재설정하는 paired-validation으로 별도 수행한다.

최종 비교는 `runs/paired-validation.json`에 있다. 기본 모델과 epoch1/2/3에 같은 상태·메모리·생성 설정·예제별 시드를 사용했다. JSON 문법은 모두 8/8이지만, 강화한 현재 규칙으로 원시 결과를 다시 검사하면 모두 6/8이다. LoRA 품질이 기본 모델보다 전반적으로 우수하다고 결론내릴 근거는 아직 부족하다. `config/serving.json`은 epoch3을 개발 후보로만 지정한다. 의미 검토에서 정중하지 않은 거절, 없는 별명 추측, 어색한 운동 안내, 사진/섭취 구분을 다시 흐린 응답을 확인했다.

기억 유무 비교는 어댑터 비교와 분리해 3쌍(취향·목표·경험)으로 실행했다. `runs/memory-ablation.json`에 동일 난수/질문에서 기억 유무만 바꾼 원시 결과가 있다. 작은 합성 사례이므로 검색 품질 전체에 대한 정확도는 산출하지 않았다.

다중 턴 개발 시험은 20흐름×10턴, 모든 흐름 두 세션이다. 31분 간격은 테스트 시계로 재현했다. 변화 8/8, 유지 8/8의 상태 규칙을 충족했고 정정·삭제 4흐름을 실행했다. 200턴 중 추가 생성 14턴, fallback 2턴, HTTP 오류 0건. 200턴을 200개 독립 최종 시험으로 세지 않았다. 이 결과는 자연어 의미 정확도 99%라는 뜻이 아니다. 규칙과 보호 기능의 후속 수정은 표적 회귀 시험으로 다시 확인했다.

자동 시험은 최종 21개 통과했다. 실제 PostgreSQL/BGE-M3와 제어 가능한 가짜 생성기로 오류·동시성·권한 경계를 시험했으며, 실제 Qwen 검증은 별도 통합/다중 턴/HTTP 파일에 기록했다. DB 장애, OOM, timeout은 제어된 오류 주입 시험이다. 실제 GPU 학습에서는 OOM 예외가 발생하지 않았다.

실제 통합 대화: 취향 저장·기억 근거 ID·취향 정정·삭제, 과제 대행 거절, 일반 운동 루틴, 기록 없음, 퀘스트 제안→수락→확인된 500걸음→보상 5점 확인. 운동/음식 입력은 합성 로컬 생산자 이벤트이며 실제 웨어러블 측정이 아니다. 개발 강제 상태에서는 존댓말/장난/새침함/가벼운 비속어/비속어 금지를 비교했다. 강제 상태 시험을 자연 성장으로 보고하지 않는다.

관측한 실패: 기본 모델의 없는 별명 기억, 사용자를 몽글이로 부르는 혼동, 불필요 운동 권유. 파일럿에도 어색한 표현, 정중하지 않은 거절, 삭제 뒤 취향을 아는 듯한 답, 채팅 운동 보고를 확인 완료처럼 서술한 사례가 있었다. 원본 결과를 보존하고 상태별 지시 및 응답 검증을 보완했다. 정상 JSON이라고 의미까지 맞는 것으로 세지 않는다. 모든 서술의 의미적 근거를 완전히 판정하는 검증기는 아니다.

실제 HTTP 시험에서 기억 ID를 인용하면서도 기록이 없다고 답한 오류도 발견했다. 이를 검사에 추가했고, 1회 보정 후에도 실패하면 조건에 맞는 짧은 원본 기억을 인용하는 fallback을 제공한다. 이 fallback은 모델 성공으로 세지 않으며 상태를 바꾸지 않는다. 원시 모델의 문제를 서버 보호 기능으로 숨겨 성능 점수에 포함하지 않는다.

추가로 수락하지 않은 후보를 ‘남은 퀘스트’라고 말하는 오류와 ‘알아. 기록은 없어’라는 모순된 응답을 차단했다. 일반 인사·취향 대화에는 확인된 운동 근거나 명시적 퀘스트 요청이 없는 한 퀘스트 후보를 제공하지 않는다. 전체 20흐름/체크포인트 비교 이후에 추가한 보호 기능은 자동 회귀 시험과 최종 실제 HTTP 재시험으로 검증하며, 20흐름 전체를 현재 코드에서 다시 수행했다고 주장하지 않는다.

현재 산출물은 실행 가능한 로컬 파일럿이다. 800/100/200 데이터 확장·독립 최종 test200·사람 품질 검수·팀 인증/DB/Unity 실연동·실제 성장/보상 규칙·Docker 재시작은 미완료 또는 미검증이다. 소량 검증 결과로 90%/98% 품질 목표를 달성했다고 주장하지 않는다.

세부 원시 결과: `runs/baseline-validation.json`, `runs/lora-validation.json`, `runs/real-integration.json`, `runs/real-integration-v2.json`, `runs/flows-development.json`, `runs/pilot-20260929/metrics.jsonl`. 운영 대화는 이 평가 파일에 자동 수집하지 않는다.

최종 실제 HTTP 재시험(`runs/http-smoke-final-v3.json`)은 완료했다. 기억 없음 → 걷기 취향 저장 → 실제 ID를 인용한 걷기 회상 → 명확한 자연어 삭제 → 삭제 후 기록 부재 응답, 다른 사용자 소유권 차단을 확인했다. 삭제 후 마지막 답변은 모델 두 번이 검증에 실패해 서버의 기록 부재 fallback을 사용했으며, 모델 자체의 기억 환각 문제가 모두 해결된 것은 아니다. 현재 API health는 Qwen3.5-9B BF16 LoRA loaded=true, pgvector 0.8.2, status=ok다.

현재 서버는 `127.0.0.1:8000`, DB는 `127.0.0.1:55432`에서 실행 중이다. 서버 로그는 `runs/api-ready-20260929.stderr.log`, 현재 worker PID는 `runs/server-worker.pid`. `START_HERE.md`의 CLI 명령으로 별도 새 펫을 만들어 대화할 수 있다. 공개 배포나 팀 운영 DB 연결은 하지 않았다.

다음 외부 입력/남은 검증: 연구실 원본 train240/val60·과거 어댑터가 있다면 전달 가능한 경로, 공개 대화 데이터의 적법한 다운로드·이용 조건, 팀 인증/활동 이벤트/보상 규격, 사람이 검수한 확장 데이터와 독립 동결 test200이 필요하다. 현재는 34건 파일럿으로 학습 가능성과 연결을 검증한 단계다. 학습을 더 오래 돌리는 것만으로 품질을 보장하지 않는다.
